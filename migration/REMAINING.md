## 六、冻结种子回归：做了什么，卡在哪（2026-11-14）

计划 §10 第 8 条要「固定种子的模拟/决斗/Boss/秘境回归稳定」。这一轮把它拆成两层，结果一层成、一层卡。

### 已成：规则层冻结样本

`OshimaBot.Tests/SeedScenario.cs` + `Fixtures/Seeded/regression.json`：22 条探针，
同种子逐值比对。覆盖抽卡（命中率 / 8 类产出 / 7 档品质 / 逐抽序列）、签到（天数阶梯 + 品质倾向）、
探索（5 档星级的分布与收益）、秘境（7 类 × 5 难度 × 单人/满编）、市场（手续费 + 两位小数展示口径）、
钻石兑换、分解返还、锻造（单一产地 / 混合产地 / 材料不足 / 产物抽取）、赛马、突破与升级三张消耗表、
运势哈希、商店日 4:00 切点，外加十连端到端（掷骰 → 入包 → 定价 → 橙色以上锁定）。

它的价值在于**断言具体值**：其余测试断言性质（区间、上限、等价样例），
概率表从 3.06% 改成 3.1%、返还从 8 改成 10、手续费口径带回 `Math.Max(1, …)`，性质测试全过、冻结样本当场报错。

防绕过的三道闸：

1. `digest`（`id\t值` 排序后 SHA-256）——手改数字而不重新生成，测试与 `check_claims.py` 都会拦；
2. 探针白名单（`SeededRegression_CoversEveryProbe`）——不能靠删探针让快照通过；
3. `SeededRegression_IsStableWithinProcess`——同进程跑两遍必须一致，
   谁在探针里混进 `Random.Shared` 或 `DateTime.Now`，这条先红。

重新生成（确认改动有意之后）：`OSHIMA_UPDATE_SEEDS=1 dotnet test --filter SeededRegression`。

### 模拟层：不改 Core，改测试形态

`FunGameSimulation.SeedOverride` 有，注释写着「同种子可复现整局」，但**实测不成立**：

| 试验 | 结果 |
|---|---|
| 同进程连跑 4 局（`SeedOverride=20261114`，混战） | 消息条数 44 / 59 / 54 / 49，摘要全不同 |
| 三个独立进程各跑 1 局 | 条数 43 / 50 / 56，摘要全不同 |
| 关掉周期空投（`EnablePeriodicDrop=false`） | 仍然不同（36 / 33 / 44） |
| 首个分歧位置 | 第 60 回合附近，**局内决策层** |

Core 不在本仓、改不了（也不该为了测试去改引擎），所以这里换形态而不是等修：

**能冻的冻死。** 开局（选人 + 首次空投 + 前几个回合的结算）是纯种子驱动的，
三次运行**逐字相同**，于是把第 1 块消息的 SHA-256 冻结进 `Fixtures/Seeded/simulation.json`。
它抓「空投规则 / 装备池 / 开局等级」被改动——这些正是数值调试最容易顺手碰的地方。

**冻不住的划边界。** 整局总伤害实测 234k–416k（1.8 倍）、每回合伤害 509–986（1.9 倍），
这不是「误差」，是决策分岔的必然后果，锁它只会造出一个随机失败的测试。
真正稳的只有「该有人死、该结束」（十余次采样击杀 18–19、回合 384–733），
于是只断言击杀数与回合数落在手写区间里。区间是**手写**的——自动测出来的区间等于没有门禁。

**措辞也改了。** 战报首行原本写「同种子可复现整局」，是句空头承诺；
现在写「同种子可复现开局与配装；局内决策可能有差异」，说到做到。

挡住什么、挡不住什么，写在测试注释里，不装：
结构性坏掉（伤害/技能全失效 → 没人死 → 回合数飙升）会红；
「暴击倍率 1.5 → 1.6」这种微调不会红，那需要先把决策随机流钉死。

### 给 Core 的三条建议（本仓不做，供上游参考）

按「改动最小 + 收益最大」排序，前两条做完，整局逐字复现大概率就成立了：

1. **`AIController` 的候选收集别落回枚举序**（`Model/Controller/AIController.cs:190-250`）。
   现在用 `Task.Run` 并行评估每个移动格、塞进 `ConcurrentBag`，最后按
   「分数 → 行动类型 → 移动格 Id → 技能 Id → 物品 Id → 目标数」排序。
   没有地图时大量 `TargetMoveGrid.Id` 相同（默认值），同分候选就落回 bag 的枚举顺序。
   建议给每个候选再加一条稳定键（例如「移动格坐标 X,Y」或提交序号），并在
   `Task.WaitAll` 之后先 `OrderBy` 再取值。
2. **`Region.Weather` 的随机源**（`Entity/Explore/Region.cs:36`）。
   内容初始化时用 `Random.Shared` 掷天气，跨进程不可控，且让内容初始化不可复现。
   建议改成接收 `IRandomSource` 或由调用方注入种子——现在天气只用于显示，
   所以这一步不急，但它确实让「同一天不同进程的地区数据」有差异。
3. **让内容构造能接受显式随机源**（`OshimaBot.Content/Units/RegionUnit.cs:14-19`、
   `RegionCharacter.cs:17-24`、`Characters/CustomCharacter.cs:15-24`）。
   这些构造函数用 `Random.Next` 掷 ATK/HP/MP/SPD/HR/MR，此时 `GamingQueue` 还是 null，
   于是走 `Random.Shared`：**探索遇敌的属性每个进程都不同**，同种子打同一只怪属性不一样。
   这条与我们自己的内容包有关，等 §六 的隔离做完可以顺手改。
